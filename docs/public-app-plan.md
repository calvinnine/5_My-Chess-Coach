# 공개 서비스 전환 설계

목표: Chess.com 사용자가 자기 아이디를 입력하면 지금 이 앱을 그대로 쓸 수 있게 한다.

이 문서는 **측정 결과에 근거한 설계안**이다. 추정으로 정한 것은 그렇게 표시했다.

---

## 1. 결론 먼저

**브라우저에서 Stockfish WASM을 돌린다.** 서버는 동기화와 저장만 맡는다.

이 한 줄이 전체 설계를 결정한다. 근거는 아래 측정치다.

### 1.1 왜 서버 분석이 불가능한가

지금 형 계정 기준 실측: 래피드 1판 = 약 1분 CPU (standard, depth 16, 4스레드).

| 사용자 | 1인당 10판 | 필요 CPU |
|---|---|---|
| 10명 | 100판 | 100분 |
| 100명 | 1,000판 | 약 17시간 |
| 1,000명 | 10,000판 | 약 7일 |

서버리스(Vercel 등)는 실행 시간 제한과 네이티브 프로세스 제약 때문에 애초에 안 되고,
전용 워커를 두면 저 CPU 시간이 그대로 청구서가 된다. 가이드 §3.2가 "처음부터
클라우드로 만들지 않는 이유"로 지적한 지점이다.

### 1.2 브라우저가 감당할 수 있는가 — 실측

`stockfish` npm 패키지(v18.0.8)의 WASM 빌드를 같은 포지션·같은 깊이로 측정했다.
(depth 16, MultiPV 2, 6개 미들게임 포지션, M-series Mac)

| 엔진 | 총 시간 | 포지션당 | 속도 |
|---|---:|---:|---:|
| 네이티브 full (1스레드) | 4.3s | 0.71s | 527 kN/s |
| 네이티브 full (4스레드) | 3.7s | 0.62s | 2,147 kN/s |
| **WASM lite-single (1스레드)** | **2.9s** | **0.48s** | **1,083 kN/s** |
| WASM lite (4스레드) | 2.8s | 0.47s | 4,374 kN/s |

**WASM lite-single이 네이티브 full보다 빠르다.** 예상과 반대인데, 이유는 `lite`
빌드가 **작은 NNUE 평가망**을 쓰기 때문이다. 노드당 평가가 가벼워서 같은 깊이에
더 빨리 도달한다. 대신 노드당 정확도는 낮다.

실용적 함의: 40수 게임(약 80포지션)이 브라우저에서 **약 40초**. 지금 서버에서
걸리는 시간과 같은 자릿수인데, 서버 CPU는 0이다.

### 1.3 약한 평가망을 써도 코칭 결론이 유지되는가 — 실측

형의 실제 게임에서 뽑은 40개 포지션으로 네이티브 full과 WASM lite를 비교했다.

| 항목 | 결과 |
|---|---|
| 최선수 일치 | 30/40 (75%) |
| 평가 차 중앙값 | **13cp** |
| 평가 차 90퍼센타일 | **35cp** |
| 수 등급 판정 일치 | 32/39 (82%) |

해석:

- 평가 차 중앙값 13cp, 90퍼센타일 35cp는 **앱의 가장 낮은 임계값(50cp)보다 작다.**
  즉 "중대 실수(200cp+)", "실수(100cp+)", 핵심 장면 선별 같은 **큰 판단은 흔들리지
  않는다.**
- 불일치 18%는 대부분 경계선이다. 손실이 48cp냐 52cp냐에 따라 양호/부정확이 갈린다.
  이건 코칭 결론(반복 약점, 훈련 과제)에 영향을 주지 않는 층위다.
- 최선수 25% 불일치도 대부분 **평가가 거의 같은 두 수** 사이의 선택이다.

**판단**: 공개 서비스의 기본 엔진으로 lite-single을 쓸 근거가 충분하다. 다만
`analysis_version`에 엔진 종류를 반드시 남겨서, 나중에 네이티브 분석과 섞였을 때
구분할 수 있어야 한다. (이미 그렇게 하고 있다.)

### 1.4 빌드 선택

| 빌드 | wasm 크기 | 스레드 | COOP/COEP 필요 |
|---|---:|---|---|
| full | **108MB** | O | **필요** |
| full-single | 108MB | X | 불필요 |
| **lite-single** | **7.0MB** | X | **불필요** |
| lite | 6.8MB | O | **필요** |
| asm.js | 10MB | X | 불필요 |

- full 계열 108MB는 웹앱에서 **논외**다. 첫 방문에 100MB를 받게 할 수 없다.
- 멀티스레드 빌드는 `SharedArrayBuffer`가 필요하고, 그러려면 사이트 전체에
  **cross-origin isolation(COOP/COEP) 헤더**를 걸어야 한다. 이건 외부 리소스
  임베드를 깨뜨리는 등 부작용이 있고, 측정상 lite-single로도 충분히 빠르다.
- **결정: `lite-single` 단일 채택.** 7MB는 최초 1회 다운로드 후 캐시된다.
  구형 브라우저 폴백으로 asm.js를 둘 수는 있으나 MVP에서는 생략한다.

## 2. 코드 변경 범위

지금 모듈 경계를 지켜둔 덕분에 **판정·코칭 로직은 한 줄도 안 바뀐다.**

| 모듈 | 브라우저에서 | 조치 |
|---|---|---|
| `analysis/eval.ts` | 그대로 동작 (순수 TS) | 없음 |
| `analysis/themes.ts` | 그대로 (chess.js) | 없음 |
| `analysis/review.ts` | 그대로 (순수 TS) | 없음 |
| `coaching/patterns.ts` | 그대로 (순수 TS) | 없음 |
| `coaching/training.ts` | 그대로 (순수 TS) | 없음 |
| `pgn/parse.ts` | 그대로 (chess.js) | 없음 |
| `analysis/analyzer.ts` | `UciEngine` 구체 타입에 의존 | **인터페이스로 분리** |
| `engine/uci.ts` | `node:child_process` | Node 전용으로 유지 |
| `coaching/dashboard.ts` | DB 접근 | 서버 유지 |
| `db/*` | SQLite 로컬 | 다중 사용자 저장소로 교체 |

### 2.1 핵심 리팩터 — Engine 인터페이스

지금 `analyzeGame(pgn, color, engine: UciEngine, ...)`이 구체 클래스를 받는다.
이걸 인터페이스로 낮춘다.

```ts
// src/lib/engine/types.ts
export interface AnalysisEngine {
  readonly versionName: string;
  evaluate(
    fen: string,
    opts: { depth?: number; movetimeMs?: number; signal?: AbortSignal },
  ): Promise<EvaluateResult>;
}
```

`UciEngine`(Node)는 이미 이 모양이다 — `implements`만 붙이면 된다.
새로 만들 `WasmEngine`(브라우저)이 같은 인터페이스를 구현한다.

`analyzer.ts`의 시그니처만 `engine: AnalysisEngine`으로 바꾸면 끝이다.
**호출부·판정 로직·테스트 모두 그대로다.**

### 2.2 WasmEngine 구현 시 주의점 (직접 확인한 것)

측정 과정에서 실제로 밟은 함정들이다. 구현할 때 그대로 적용한다.

1. **출력 훅은 `print`가 아니라 `listener`다.**
   이 빌드는 `Module.print`를 자체적으로 덮어써서 `listener`로 위임한다.
   Web Worker 안에서는 기본값이 `postMessage`라 자연스럽게 연결된다.
2. **명령 전송은 반드시 비동기로 미룬다.**
   `ccall`은 `go`를 제외하면 **동기 실행**이라, 리스너를 등록하기 전에 `uciok` /
   `readyok`이 방출되어 영영 기다리게 된다. 패키지 자체도 `setImmediate`로 감싼다.
   → 리스너를 **먼저 등록하고** 나중에 send 하는 순서를 지킬 것.
3. **`lite-single`은 `Threads` 최대값이 1이다.** `setoption name Threads`를 보내면
   무시되거나 에러가 된다. 보내지 않는다.
4. Worker에서 돌린다. 메인 스레드에서 돌리면 UI가 통째로 멈춘다.

### 2.3 분석 결과를 누가 저장하는가

브라우저가 계산하고, **결과만 서버로 올린다.**

```
브라우저: PGN → WasmEngine → analyzeGame() → AnalyzedMove[] → buildReview()
   ↓ POST /api/games/:id/analysis  (move rows + review)
서버: Zod 검증 후 저장
```

**보안 주의**: 클라이언트가 보낸 값을 그대로 믿으면 안 된다. 서버에서 최소한
다음은 검증한다.

- `ply`가 연속인지, `san`/`uci`가 저장된 PGN과 일치하는지 (chess.js로 재생)
- `centipawn_loss >= 0`, 등급이 손실 구간과 맞는지
- 한 게임의 move 수가 PGN의 수와 같은지

이건 새 코드지만 어렵지 않다. 판정 함수를 서버에서 다시 돌려 대조하면 된다
(엔진 없이 가능 — `classifyMove`는 순수 함수다).

## 3. 다중 사용자 설계

### 3.1 계정은 필요한가

**MVP에서는 불필요하다.** Chess.com 공개 데이터라 아이디만 있으면 조회된다.
`players.username`이 이미 고유키이므로 그대로 다중 사용자 키가 된다.

계정이 필요해지는 시점은 **"내 메모"를 저장할 때**다. 메모는 사용자가 쓴 사적인
내용이고, 아이디만 알면 남의 메모를 읽을 수 있으면 안 된다.

→ 단계적 접근:
- **1단계**: 메모 없이 공개. 동기화·분석·대시보드만.
- **2단계**: 메모 기능은 로그인 사용자에게만. (Chess.com OAuth는 없으므로
  이메일 매직링크 또는 GitHub/Google OAuth)

### 3.2 저장소

로컬 SQLite → 다중 사용자에서는 부적합하다. 후보:

| 후보 | 장점 | 단점 |
|---|---|---|
| **Turso (libSQL)** | Drizzle 스키마 **거의 그대로**, SQLite 방언 유지 | 별도 서비스 |
| Neon / Supabase (Postgres) | 표준, 무료 티어 넉넉 | 마이그레이션 재작성 |

**추정**: Turso가 전환 비용이 가장 낮다. Drizzle의 `dialect: "sqlite"`를 유지하고
드라이버만 바꾸면 되므로 마이그레이션 파일도 재사용 가능하다. 다만 실제로 시도해
보지 않았으므로 확정은 아니다.

스키마 변경은 **거의 없다**. `games.player_id`가 이미 있어서 사용자별 격리는
질의 조건만 추가하면 된다.

### 3.3 Chess.com API를 공유 자원으로 다루기

지금은 형 혼자 순차 요청이라 문제가 없다. 서버 한 IP에서 수백 명 몫을 쏘면
**차단당한다.** 필요한 것:

1. **전역 직렬 큐** — 지금 `ChessComClient`가 인스턴스 단위로 직렬화한다.
   서버에서는 **프로세스 전역 단일 큐**로 올려야 한다.
2. **사용자별 쿨다운** — 같은 아이디 재동기화는 예: 5분에 1회.
3. **아카이브 캐시 공유** — 이미 `sync_cache`에 ETag를 저장한다. 다중 사용자에서도
   URL 키가 그대로라 자연히 공유된다. (단 D7 결정에 따라 아카이브 목록은 비캐시)
4. **정직한 User-Agent** — 앱 이름과 연락처. 이미 구현되어 있고, 공개 서비스에서는
   **실제 연락 가능한 주소**여야 한다.

### 3.4 어뷰즈 방지

누가 `hikaru`를 입력하면 지금 구조에선 600판이 큐에 들어간다.

- 1회 동기화 상한: 최근 N개월 또는 최대 M판 (기본값을 보수적으로)
- 분석은 브라우저에서 도니 서버 부하는 없지만, **결과 업로드 크기**에 상한이 필요
- 아이디당 저장 게임 수 상한 (예: 1,000판)

## 4. 단계별 실행 계획

각 단계는 **그 자체로 동작하는 상태**로 끝난다.

### ✅ Phase A — 엔진 추상화 (완료)
1. ✅ `engine/types.ts` — 런타임 비의존 타입 + UCI 파싱 + `AnalysisEngine`
2. ✅ `engine/base.ts` — `LineEngine`이 UCI 대화 전체를 담당, 하위 클래스는
   transport만 제공
3. ✅ `UciEngine`(파이프) / `WasmEngine`(Worker) 두 구현
4. ✅ `analyzer.ts`가 인터페이스에 의존 — 판정·코칭 로직 변경 0
5. ✅ 교차 검증 테스트 `tests/unit/engine-parity.test.ts`

**측정된 완료 기준**:
- 기존 테스트 전부 통과 (97 → 108개로 증가)
- 같은 게임 평가 차 중앙값 < 50cp
- 승패 방향 일치 > 90%
- **결정적 장면(분기점) 정확히 일치**

발견한 함정 (D16): `stockfish` npm 패키지가 `node_modules/.bin/stockfish` 심링크를
만들어 자동 탐지가 네이티브 대신 WASM을 잡았다. `locateEngine`이 node_modules를
건너뛰도록 수정.

주의: vitest 워커 하나에 WASM 엔진 인스턴스를 둘 만들면 죽는다. 파일을 분리해
워커당 하나만 뜨게 했다.

### Phase B — 브라우저 분석 경로 (다음)
0. 빌드 시 `node_modules/stockfish/bin/stockfish-18-lite-single.{js,wasm}` 를
   `public/engine/` 로 복사 (패키지 전체 239MB 중 7MB만 배포)
1. `createBrowserEngine("/engine/stockfish-18-lite-single.js")` 연결
2. 진행률 UI를 서버 폴링에서 워커 메시지로 전환
3. 결과 업로드 API + 서버측 검증
4. 엔진 없는 환경(구형 브라우저) 안내

완료 기준: 로컬 앱에서 Stockfish 미설치 상태로도 분석이 된다.

### Phase C — 다중 사용자
1. 저장소 전환 (Turso 우선 시도)
2. 사용자별 격리 질의
3. 전역 API 큐 + 쿨다운 + 상한
4. 배포

## 5. 지금 구조에서 그대로 살아남는 것

전환해도 **재작성이 필요 없는 자산**:

- 평가 관점 정규화와 메이트 표현 (D2, D3)
- 중요도 공식과 붕괴 지점 판정 (D4, D5, D6)
- 패턴 승격 기준과 신뢰도 계산
- 훈련 과제 생성 규칙
- 코치·봇 판별 (D12)
- 한국어 조사 처리 (D14)
- 단위 테스트 97개 중 엔진 비의존 테스트 전부

전환 비용이 낮은 이유는 가이드가 요구한 **모듈 경계**(chesscom / pgn / engine /
analysis / coaching)를 지켰기 때문이다. UI가 평가를 계산하지 않는다는 규칙도
브라우저 전환에서 값을 한다.

## 6. 열린 질문

- **엔진 선택을 사용자에게 노출할 것인가?** lite-single 고정이 단순하지만,
  데스크톱 사용자에게 "정밀 모드(full-single, 108MB)"를 옵션으로 줄 수도 있다.
  → 추정: MVP에서는 숨기고, 요청이 있으면 추가.
- **분석 결과를 서버에 저장할 것인가, 브라우저에만 둘 것인가?**
  IndexedDB만 쓰면 서버 비용이 0에 수렴하지만 기기 간 동기화가 안 된다.
  → 추정: 게임 메타데이터는 서버, 분석 결과도 서버(공유 캐시 효과가 큼 —
  같은 게임을 여러 사람이 분석할 일은 없지만, 재방문 시 재분석을 피할 수 있다).
- **Lichess 연계**를 같이 열 것인가. 데이터 모델은 이미 `external_url` 기반이라
  확장 여지가 있다.
